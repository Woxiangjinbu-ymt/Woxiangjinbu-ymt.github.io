# DeepSeek-V2 精读报告

> **一句话核心主张：** DeepSeek-V2 通过 MLA 压缩推理时的历史状态，通过 DeepSeekMoE 将模型总容量与每 token 计算量解耦，再用路由、负载均衡、分布式训练和对齐机制解决这些架构带来的工程副作用，最终得到一个总参数 236B、每 token 激活 21B、支持 128K 上下文的稀疏语言模型。

这篇论文最值得学习的不是某一条孤立公式，而是一套完整的系统设计思路：先通过新架构获得理论上的容量或效率收益，再逐一处理位置编码、专家通信、负载不均、训练稳定性和部署精度等现实问题。

可以把全文压缩成一句更具机制性的总结：

> **MLA 解决“历史状态存不下”，DeepSeekMoE 解决“模型容量增大后每个 token 算不起”，配套工程机制则解决“理论收益在真实硬件上跑不出来”。**

## 2. 问题背景：为什么需要 DeepSeek-V2

扩大语言模型通常能提高能力，但会同时产生三类成本。

### 2.1 模型能力与每 token 计算量绑定

Dense Transformer 中，每个 token 都经过全部 FFN 参数。扩大模型容量意味着同步增加每 token FLOPs、训练时间和推理计算。理想状态是保留大模型的总知识容量，但只让每个 token 使用与它最相关的一小部分参数。

### 2.2 KV Cache 限制生成服务

自回归生成需要保存所有历史 token 在每一层的 Key 和 Value。标准多头注意力 MHA 为每个Attention head保存独立K/V，序列越长、层数越多、batch越大，KV Cache占用越高。它会直接限制最大batch size和并发吞吐。

MQA和GQA通过共享K/V降低缓存，但论文的受控实验显示，这种共享可能损害模型能力。DeepSeek-V2希望在接近甚至超过MHA能力的同时，把缓存压到接近少数组GQA的规模。

### 2.3 稀疏MoE引入新的系统问题

MoE降低激活计算，但并不是“免费扩容”。专家被分散到多个设备后，token需要跨设备发送；自动学习的路由还可能集中到少数专家，产生路由坍缩、设备负载不均和通信热点。因此，只有把路由与分布式训练共同设计，稀疏计算才能转化为实际训练效率。

## 4. 整体模型架构

DeepSeek-V2总体仍是Pre-Norm Transformer，每个Block保留Attention和FFN两个子层，但分别替换为MLA和DeepSeekMoE。

```text
输入隐藏状态 h_t
    │
    ├─ RMSNorm
    │    └─ MLA Attention
    │
    ├─ Residual Add → u_t
    │
    ├─ RMSNorm
    │    └─ DeepSeekMoE FFN
    │         ├─ 2个共享专家：始终参与
    │         └─ 160个路由专家：每token选择6个
    │
    └─ Residual Add → 输出隐藏状态 h'_t
```

### 4.1 关键规模配置

| 配置 | DeepSeek-V2 |
|---|---:|
| Transformer层数 | 60 |
| 隐藏维度 | 5120 |
| Attention heads | 128 |
| 每head维度 | 128 |
| KV压缩维度 | 512 |
| Query压缩维度 | 1536 |
| 解耦RoPE维度 | 64 |
| 每个MoE层的共享专家 | 2 |
| 每个MoE层的路由专家 | 160 |
| 每token激活路由专家 | 6 |
| 总参数 | 236B |
| 每token激活参数 | 21B |

除第一层FFN外，其余FFN均替换为MoE层。第一层仍为Dense FFN。

### 4.2 236B与21B应该怎样理解

236B表示模型拥有的全部参数，包括Attention、第一层Dense FFN、所有共享专家以及所有路由专家。21B表示一个token完成一次前向传播实际经过的公共参数、共享专家和被选中路由专家。

因此，“激活21B”只描述每token计算路径，不意味着部署时只需存储21B。系统仍需保存全部236B参数，因为不同token可能选择不同专家。

需要严格区分：

- **总参数**决定模型总容量和权重存储；
- **激活参数**影响每token主要计算量；
- **KV Cache**由Attention结构、层数、序列长度和batch决定；
- **通信成本**由专家放置及token路由覆盖的设备决定。

## 5. 核心创新一：Multi-head Latent Attention

### 5.1 MLA真正改变了什么

标准MHA会为每个历史token缓存所有Attention head的完整K和V。MLA不再把完整K/V作为历史状态，而是先将它们联合压缩为一个较小的潜向量：

\[
c_t^{KV}=W^{DKV}h_t
\]

需要内容Key和Value时，再由这个潜向量上投影得到：

\[
k_t^C=W^{UK}c_t^{KV},\qquad v_t^C=W^{UV}c_t^{KV}
\]

这可以理解为改变了Attention历史状态的“存储格式”：模型在训练中仍学习丰富的多头表示，但生成时保存的是能够恢复K/V的低维公共潜表示。

### 5.2 为什么不需要反复恢复完整K和V

如果每个新token到来后都把所有历史潜向量重新上投影成完整K/V，缓存虽然变小，计算却会变重。MLA利用矩阵乘法结合律，把Key上投影合并到Query侧，把Value上投影合并到输出投影侧。

直观地说，原本的：

```text
Query ×（上投影后的历史Key）
Attention权重 ×（上投影后的历史Value）
```

可以重排为：

```text
预先变换后的Query × 历史KV潜向量
潜向量聚合结果 × 合并后的输出投影
```

这些上投影矩阵是训练完成后固定的，因此可以提前合并，避免每次生成显式恢复历史K/V。

### 5.3 为什么还需要解耦RoPE

RoPE使用随token位置变化的旋转矩阵。如果直接把RoPE放在压缩内容Key路径中，位置矩阵会夹在固定投影之间。由于矩阵乘法不能随意交换，Key上投影便无法再被吸收到Query投影中，历史Key需要重新计算，MLA的推理优势会被破坏。

DeepSeek-V2因此将Attention表示分成内容与位置两部分：

\[
q=[q^C;q^R],\qquad k=[k^C;k^R]
\]

- \(q^C,k^C\)负责内容匹配，不使用RoPE，可以保持低秩压缩和矩阵吸收；
- \(q^R,k^R\)专门携带位置信息，并应用RoPE；
- 每个head拥有自己的位置Query，而位置Key在各head间共享。

推理时缓存的是 \(c^{KV}\) 和较小的 \(k^R\)，而不是完整多头K/V。

### 5.4 缓存规模与实际部署

不同Attention机制每token、跨全部层的理论缓存元素数为：

| Attention | KV Cache元素数 |
|---|---:|
| MHA | \(2n_hd_hl\) |
| GQA | \(2n_gd_hl\) |
| MQA | \(2d_hl\) |
| MLA | \((d_c+d_h^R)l\) |

按DeepSeek-V2配置，MLA缓存量等价于约2.25组GQA。相对同配置MHA，其理论元素数量约减少98.24%。论文报告的93.3%则是DeepSeek-V2与DeepSeek 67B实际部署的字节数比较，基线配置和存储精度不同；DeepSeek-V2还将KV Cache量化到平均约6 bit，因此两种比例并不矛盾。

### 5.5 MLA的证据与边界

Appendix D的Table 9在两个MoE规模上保持主要条件接近，只替换MHA和MLA。这是论文中最接近架构因果证据的实验：

- 小规模模型的缓存由110.6K降至15.6K元素；
- 大规模模型由860.2K降至34.6K元素；
- MLA在两个规模的大多数困难Benchmark上达到更高结果，但小规模C-Eval略低于MHA。

因此，论文较有力地证明了MLA能显著压缩缓存且没有表现出典型MQA/GQA式的能力退化。不过，实际吞吐收益仍然混合了缓存量化、FP8、Kernel优化和batch size变化，不能全部归因于MLA本身。

## 6. 核心创新二：DeepSeekMoE

### 6.1 共享专家与路由专家

一个token经过DeepSeekMoE时：

1. 两个共享专家始终参与，负责通用知识；
2. 路由器计算token与160个路由专家的亲和力；
3. 选择得分最高的6个路由专家；
4. 共享专家输出与路由专家加权输出相加，再通过残差连接形成Block输出。

其中，路由专家的gate value并不是另一套独立选择机制：top-K由亲和力排序确定；被选专家的gate value等于其亲和力，未选专家为0。

### 6.2 两个结构动机

**细粒度专家划分**将少量大专家切分为更多、更小的专家，并相应激活多个小专家。即使保持总专家参数和激活专家参数近似不变，更细的专家也能为不同token形成更灵活的组合，使知识分工更精确。

**共享专家隔离**把通用知识交给固定专家，减少多个路由专家重复学习相同公共知识，从而让路由专家把有限容量用于差异化专业知识。

### 6.3 Device-limited Routing

普通top-K可能把6个目标专家分散到很多设备，导致一个token触发多次跨设备发送。DeepSeek-V2先选出最多 \(M\) 个包含高亲和力候选专家的设备，再只从这些设备中选择最终top-K专家。

训练配置中路由专家均匀部署到8个设备，\(M=3\)。最终激活专家数仍然是6，但这些专家最多分布在3个设备上。该机制给每个token的通信范围设置上界；代价是可能排除未选设备上的高分专家。论文观察到 \(M\ge3\) 时性能与无限制路由大致相当。

### 6.4 三类负载均衡

DeepSeek-V2从三个层次约束路由：

| 损失 | 平衡对象 | 防止的问题 |
|---|---|---|
| Expert-level balance | 单个专家的实际负载与平均路由倾向 | 少数专家垄断token、其他专家训练不足 |
| Device-level balance | 一个设备上所有专家的计算负载 | 某些设备计算过载并拖慢同步 |
| Communication balance | 各设备接收token的通信量 | 某些设备成为通信热点 |

设备计算与通信不能互相替代：一个token可能在同一设备访问多个专家，只发生一次设备发送，却产生多份专家计算。

辅助损失通过对高负载专家或设备的路由概率施加惩罚，推动路由器分散流量。但权重过大会迫使路由过度均匀，牺牲token与专家的真实匹配和专家专业化。

### 6.5 Token Dropping

平衡损失只是软约束，不能保证设备严格不超载。因此训练时还使用硬容量控制：

- 每个设备capacity factor设为1.0，即只处理平均计算预算；
- 超载时优先丢弃亲和力最低的token专家路径；
- 约10%的训练序列永不丢弃，使模型同时见过完整计算路径。

推理时可以根据目标选择：开启dropping换取更稳定的负载和吞吐，或关闭dropping保留完整专家贡献和模型质量。

## 7. 从预训练到对齐的完整流程

```text
8.1T token、4K上下文基础预训练
        ↓
YaRN长上下文扩展：32K训练，验证到128K
        ↓
1.5M指令数据SFT
        ↓
GRPO阶段一：数学/代码推理对齐
        ↓
GRPO阶段二：helpfulness/safety/rule人类偏好对齐
        ↓
DeepSeek-V2 Chat (RL)
```

### 7.1 数据与基础预训练

论文沿用DeepSeek 67B的数据处理流程，但扩大数据量、改进质量过滤，并增加中文数据。最终预训练语料为8.1T token，使用100K词表的BBPE tokenizer，中文token数量约比英文多12%。作者还过滤部分具有地区文化争议的内容，以降低特定价值偏置。

基础预训练的最大序列长度为4K。训练采用AdamW、warmup加分段衰减，batch size在前225B token中由2304逐步增至9216，之后保持不变。

### 7.2 长上下文扩展

基础预训练完成后，模型通过YaRN将上下文从4K扩展到128K。由于MLA把RoPE集中在 \(q^R,k^R\) 位置分支，YaRN只需作用于共享位置Key路径。

扩展阶段额外训练1000 step，训练长度为32K，YaRN配置目标为160K，论文正式验证到128K。Figure 4的NIAH测试表明模型能在128K范围内检索插入信息，但这不能等价为128K下所有多跳推理和全局理解任务均可靠。

### 7.3 SFT

SFT使用1.5M条指令数据：

- 1.2M helpfulness数据；
- 0.3M safety数据；
- 训练2个epoch；
- 学习率为 \(5\times10^{-6}\)。

SFT数据包含大量数学、代码、写作、推理和安全内容，因此Chat (SFT)相对基础模型在数学和代码任务上有明显提升。

### 7.4 GRPO强化学习

GRPO为每个问题从旧策略采样一组回答，通过组内奖励的标准化结果估计每个回答的相对优势：

\[
A_i=\frac{r_i-\operatorname{mean}(r_1,\ldots,r_G)}
{\operatorname{std}(r_1,\ldots,r_G)}
\]

它不需要PPO中通常与policy同规模的critic模型，从而降低大模型RL的显存与训练成本。目标中的clip限制新旧策略变化过大，KL项限制策略偏离reference model。

RL分为两个阶段：

1. **Reasoning alignment**：针对数学和代码，奖励来自reasoning reward model；代码可使用编译器反馈，数学可使用标准答案。
2. **Human preference alignment**：将helpfulness、safety和rule-based reward加权组合，优化通用对话偏好。

论文观察到RL提高了数学、代码和开放式生成能力，但部分标准Benchmark如BBH会下降，说明对齐存在alignment tax。

## 8. 关键训练与部署工程

DeepSeek-V2采用内部HAI-LLM框架，在H800集群上训练。

| 并行或优化 | 切分/优化对象 | 作用 |
|---|---|---|
| 16-way zero-bubble pipeline parallelism | 不同Transformer层 | 分摊模型层并减少流水线空泡 |
| 8-way expert parallelism | 同一MoE层的不同路由专家 | 分布全部专家，通过all-to-all完成token路由 |
| ZeRO-1 data parallelism | 数据并行副本的优化器状态 | 降低Adam等优化器状态的副本内存 |
| 不使用tensor parallelism | 避免切分单层大矩阵 | 减少层内高频通信；整体模型仍由pipeline和expert parallel分布 |
| 计算通信重叠 | 共享专家计算与专家all-to-all | 隐藏部分通信延迟 |
| 定制CUDA Kernel | 通信、路由、专家融合计算 | 将理论稀疏收益转化为实际MFU |
| 改进FlashAttention-2 | MLA Attention | 提高Attention执行效率 |

“不使用tensor parallelism”不是因为236B或21B参数可以全部装入一张GPU，而是因为较小的激活路径和激活重计算使单层压力可控，继续引入TP反而增加通信。全部236B专家权重仍分布在集群设备上。

实际部署时，模型权重转换为FP8，KV Cache量化到平均约6 bit。MLA减少的是KV状态维度，量化减少的是每个缓存元素的字节数，两者共同决定实际缓存。

| GRPO改善Chat能力 | Table 3–5，数学、代码和开放式对话提升 | SFT后继续RL有效 | 部分收益可能来自奖励数据，且存在alignment tax |

### 9.2 代表性结果

- 基础模型MMLU为78.5，高于DeepSeek 67B的71.3，并接近同代70B级开源Dense模型。
- 每训练1T token，DeepSeek-V2使用172.8K H800 GPU hours，DeepSeek 67B为300.6K。
- 实际部署KV Cache相对DeepSeek 67B减少93.3%。
- 单节点8张H800的最大生成吞吐超过50K token/s，输入吞吐超过100K token/s。
- DeepSeek-V2 Chat (RL)达到MT-Bench 8.97、AlpacaEval 2.0长度控制胜率38.9、AlignBench 7.91。

这些数字适合描述最终系统的能力和效率，但必须结合下面的比较边界解释。

## 10. 对比公平性与证据边界

### 10.1 与DeepSeek 67B比较什么时候合理

如果问题是“两个已经训练完成的模型，哪一个最终能力更强、每训练1T token更便宜、在同类服务负载下吞吐更高”，这种比较是合理的。它评价的是完整模型产品和系统设计。

### 10.2 什么时候不构成架构因果证据

DeepSeek-V2与DeepSeek 67B之间同时变化了：

- Dense与MoE架构；
- 总容量与激活容量；
- 训练token数量；
- 数据质量、中文比例和过滤策略；
- 上下文长度；
- 分布式训练、推理精度与Kernel实现。

因此，两者的最终Benchmark差异不能直接证明“DeepSeekMoE或MLA本身使模型更强”。要判断单一模块，应该优先查看只替换Attention的Appendix D Table 9，或此前DeepSeekMoE论文中的受控对比。

### 10.3 训练成本的分母

论文的42.5%来自“每训练1T token所需GPU hours”，是单位token成本。DeepSeek-V2最终训练了8.1T token，所以不能直接把该比例理解为整个训练项目总GPU投入下降42.5%。完整成本还需要同时知道两代模型的总训练token和实际训练过程。

### 10.4 吞吐是完整系统结果

5.76倍吞吐同时依赖MLA、较少激活计算、FP8、KV Cache量化、专家通信优化和更大batch。正确结论是“DeepSeek-V2完整部署系统的最大吞吐更高”，而不是“MLA单独带来5.76倍提升”。

## 11. 关键辨析与局限

### 11.1 最容易混淆的四组概念

1. **总参数不等于激活参数**：236B描述容量和存储，21B描述每token计算路径。
2. **理论缓存元素不等于实际显存字节**：还要考虑精度、布局、量化和运行时开销。
3. **单位token训练成本不等于完整训练总成本**：必须乘以实际训练token数量。
4. **128K NIAH成功不等于128K复杂推理成功**：前者主要是长距离检索能力。

### 11.2 作者明确承认的局限

- 预训练后知识不能持续更新；
- 仍会生成非事实信息、未经验证的建议和幻觉；
- 数据主要为中文与英文，其他语言能力有限；
- 目前只支持文本模态；
- RL对齐可能提高开放式生成，却损害部分标准任务。

### 11.3 论文尚未充分回答的问题

- 如果严格统一数据、训练token和激活FLOPs，MoE与Dense的能力差异有多大？
- MLA、KV量化、FP8和Kernel优化分别贡献了多少实际吞吐？
- Device-limited routing在更大规模、更多设备和异构集群上是否仍保持相同质量—通信权衡？
- 128K上下文下的多跳推理、跨文档综合和长输出稳定性如何？
- 在线RL优于离线RL的观察缺少完整受控比较。

## 12. 我的理解与研究启发

### 12.1 DeepSeek-V2的核心不是“稀疏”本身，而是解耦

MLA将模型表达能力与历史状态存储量部分解耦；DeepSeekMoE将模型总容量与每token计算量部分解耦。DeepSeek-V2的价值在于同时控制这两个维度，而不是单纯追求更大的总参数。

但“解耦”并不等于消除成本。MoE把Dense计算问题转化为参数存储、路由和通信问题；MLA把完整K/V缓存转化为潜向量与位置分支。好的系统设计不是让代价消失，而是把代价转移到更可控的位置。

### 12.2 核心创新必须配套处理副作用

论文呈现出很清楚的设计模式：

```text
低秩KV压缩
→ RoPE阻碍矩阵吸收
→ 解耦RoPE

细粒度专家
→ 跨设备通信增多
→ Device-limited routing

自动路由
→ 负载不均与通信热点
→ 三类平衡损失 + Token Dropping
```

这比只总结“提出MLA和MoE”更重要。研究创新往往会改变系统中的瓶颈位置，后续工作应该主动寻找新瓶颈，而不是只证明主模块在理想条件下有效。

### 12.3 对Agent与Skill研究的启发

DeepSeekMoE不能直接等同于Agent Skill，但它提供了一种值得借鉴的模块化思路：公共能力与专业能力可以分开维护，再由输入相关的路由机制选择专业模块。迁移到Skill优化时，需要进一步回答：

- 哪些程序性知识应该作为所有任务共享的基础Skill？
- 哪些知识应该拆成细粒度专用Skill？
- 路由器如何在不产生大量调用和上下文开销的情况下选择Skill？
- 如何避免少数Skill被反复调用、其他Skill得不到训练或验证？

这种联系目前只是研究启发，不是论文已经证明的结论。最小验证可以固定Agent模型和任务集，对比“单一大Skill”“共享Skill加细粒度路由Skill”，同时记录成功率、调用成本、token开销和最差任务组表现。

### 12.4 对实验设计的直接提醒

DeepSeek-V2与67B的比较说明：产品级领先和算法因果证明是两种不同证据。在自己的研究中，也应区分：

- 完整Agent系统最终是否更强；
- 提升是否确实来自Skill、Observation或工作流中的某一个创新；
- 单次推理成本、优化成本和整个实验总成本是否使用了同一分母。

这要求主结果展示完整系统价值，同时用严格消融隔离各模块贡献。

## 13. 最终总结：现在应该怎样理解 DeepSeek-V2

DeepSeek-V2仍然是Transformer，但替换了两个最关键的高成本部件：Attention使用MLA，FFN使用DeepSeekMoE。

MLA不保存完整多头K/V，而是保存低维KV潜向量；通过矩阵吸收避免恢复完整K/V，通过解耦RoPE把位置编码从内容压缩路径中分离。它解决的是长序列生成中的历史状态存储问题。

DeepSeekMoE用2个共享专家承载公共知识，用160个路由专家形成细粒度专业能力，每token只选择6个路由专家。它解决的是模型总容量和每token计算量之间的矛盾。Device-limited routing、三类负载均衡损失和token dropping进一步解决专家并行产生的通信与负载问题。

模型先在8.1T token、4K上下文上预训练，再通过YaRN和32K继续训练扩展到声明支持128K，随后使用1.5M指令数据SFT，并通过两阶段GRPO完成推理与人类偏好对齐。底层采用pipeline parallel、expert parallel、ZeRO-1、通信重叠和定制Kernel，使稀疏架构真正获得实际效率。

论文最可靠的结论是：DeepSeek-V2作为完整系统，在能力、单位token训练成本和推理吞吐之间取得了很强的综合权衡；MLA的受控实验也较好地支持了其缓存优势。需要保留的判断边界是：与DeepSeek 67B的最终对比不能单独证明架构因果，42.5%是单位token成本，5.76倍是完整部署系统收益，128K的主要直接证据是长距离检索而不是所有长上下文推理能力。
